== 1. Granularity

=== Smallest Unit of Documentation
Fumadocs takes a **component-driven compositional approach** to granularity:
* Instead of generating an entire monolithic HTML page per module, Fumadocs uses MDX components like `<AutoTypeTable path="..." name="..." />` or `<TypeTable />`.
* **Component-Level Embedding**: Developers embed precise type inspection tables directly alongside narrative guides and tutorials.
* **Property Permalinks**: Prop rows can have individual anchor targets; heading permalink links appear as sleek Lucide icons on hover.

=== Granularity Analysis
[horizontal]
Addressability Mechanism:: Component-scoped anchors (`#usage`, `#from-file`, `#typescript-compiler`).
Overload Handling:: Overloads in TypeScript definitions are rendered as stacked type signature badges inside the type table cells.
Optional Prop Differentiation:: Optional TypeScript properties receive an explicit question mark badge (`options?`) rendered with distinct opacity.
Inline vs Linked Types:: Complex types expand either into expandable popover drawers or collapsible nested rows directly inside the table.

== 2. Hierarchy Expression

=== Multi-Tier Structural Mapping
Fumadocs departs radically from classical Python autodoc layouts by adopting **modern SaaS dashboard card components**:

[cols="1,2,2", options="header"]
|===
| Level Transition | Visual Mechanism | Design Tokens Involved
| Section -> Sub-component | Left sidebar navigation with active indicator bar (`before:bg-fd-primary`). | `data-[active=true]:bg-fd-primary/10`
| Narrative -> API Specification | Embedded `<AutoTypeTable />` card surface (`rounded-xl border bg-fd-card`). | `bg-fd-card`, `border-fd-border`, `shadow-sm`
| Interface -> Property Row | Grid/Table row with Prop Name in bold monospace, Type in styled Shiki code capsule. | `text-fd-foreground`, `font-mono`
| Property -> Sub-Properties / Options | Expandable accordion row or nested popover dialog. | `<Accordion>`, Radix UI popover
|===

=== Spatial & Navigational Encodings
* *Left Sidebar*: Hierarchical navigation tree with icon prefixes (Lucide icons) and group labels (e.g. `Introduction`, `References`, `Components`).
* *Right TOC*: In-page Table of Contents with smooth scroll-spy and anchor link copy button on hover.
* *Header Navigation*: Global tab navigation switching between libraries (`Pydantic Validation`, `Fumadocs UI`, `CLI`).

== 3. Within-Level Differentiation

=== Sibling Entity Disambiguation
Fumadocs uses **visual micro-components** and **color-coded syntax tokens**:

[horizontal]
Grouping Strategy:: Categorized within MDX documents using clean `<h2>` / `<h3>` sections with Lucide icon anchors.
Kind Identifiers::
* **Type Capsule Pills**: Types are displayed inside monospace capsules (`union`, `function`, `Partial<object>`).
* **Optionality Markers**: `?` character highlighted in muted foreground color (`options?`).
* **Method vs Property**: Function signatures show arrow notation (`(input: string) => void`) directly within the type column.
Typographic Treatment:: Monospace font for both property name and type definition, but with strict visual separation (Name is unbordered; Type is encased in subtle background capsule).

[cols="1,1,2,2", options="header"]
|===
| Symbol Kind | Icon / Glyph | Badge Style / Color | Visual Distinction Mechanism
| Interface Prop | None | Bold monospace | Plain identifier on left
| Optional Prop | `?` suffix | Muted monospace text | Subtle opacity reduction on the question mark
| Function Prop | `=>` token | Styled syntax capsule | Arrow return signature in Catppuccin colors
| Union Type | `\|` token | Capsule with pipe separator | Multiple clickable type fragments
|===

== 4. Detail Layout (Symbol Anatomy)

=== Single Symbol Information Architecture
Within an `<AutoTypeTable />` or `<TypeTable />` component:
1. **Header Row**: Two clean column headers (`Prop` and `Type`, optionally `Default` and `Description`).
2. **Prop Identifier**: Monospace text name on the left.
3. **Type Descriptor**: Richly styled type signature rendered with Shiki dual-theme tokens (`--shiki-light` / `--shiki-dark`).
4. **Description / Markdown**: Inline markdown prose below the property name explaining its purpose.
5. **Default Value**: Rendered in a secondary badge if present.

=== Layout Mechanics
[horizontal]
Parameter Representation:: Modern responsive table layout with horizontal scrolling wrapper (`fd-scroll-container`) preventing page blowout on mobile.
Collapsible Elements:: Heavy use of modern interactive primitives: `<Accordion>`, collapsible code blocks with copy buttons, expandable object types.
Signature Wrapping & Formatting:: Wrapped using Shiki syntax highlighter with support for diff highlighting (`has-diff`, `diff add`).
Source Code Integration:: Copy-to-clipboard button with visual checkmark feedback (`data-checked:text-fd-accent-foreground`).

== Unique Innovations & Failure Modes

=== Standout Design Innovations
* **React Server Component DocGen**: Runs TypeScript compiler extraction at server render time via Next.js RSC, eliminating stale build artifacts and allowing runtime type caching.
* **Component-First Composition**: Documents APIs as inline interactive components (`<AutoTypeTable />`) rather than forcing entire repos into rigid auto-generated templates.
* **Dual-Theme Shiki Rendering**: Code blocks output CSS variables for both light and dark modes simultaneously (`--shiki-light`, `--shiki-dark`), completely eliminating dark-mode flash of unstyled content (FOUC).
* **Interactive Type Table Cards**: Clean rounded container boxes with copy buttons, diff decorators, and popover previews.

=== Critical Anti-Patterns / Friction Points
* **Requires Next.js / React Runtime**: Cannot be deployed as zero-JS flat HTML files on simple static web servers without a Next.js / Node build step.
* **Lack of Standalone Module Hierarchy View**: Because it is component-driven, it does not automatically generate comprehensive AST tree pages (like Rustdoc or Sphinx) without manual MDX wiring.

=== Transferable Principles for Future Autodoc Systems
1. *Zero-FOUC Dual Syntax Highlighting*: Emit light and dark theme syntax tokens simultaneously via CSS custom properties on code spans rather than recompiling HTML on theme toggle.
2. *Componentized API Embedding*: Allow API reference tables to be modularly dropped into narrative documentation alongside tutorials.
3. *Soft Container Surfaces*: Encapsulating API declarations in rounded card containers (`rounded-xl border bg-card`) creates superior visual grouping compared to infinite flat pages.
