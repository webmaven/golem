== 1. Granularity

=== Smallest Unit of Documentation
Stripe represents the **zenith of deep parameter granularity in technical documentation**:
* **Every Parameter is an Independent Node**: In `Markdoc` AST, each parameter is a typed `Element` node (`name: 'amount', type: 'integer', required: true`).
* **Nested Object Expansion**: Deeply nested properties (e.g. `payment_method_data[billing_details][address][city]`) expand hierarchically into sub-parameter trees with independent types, validation rules, and descriptions.
* **Secondary Parameter Folding**: Divides parameters into two distinct tiers: **Common Parameters** (shown upfront) and **"More parameters"** (collapsed under `<details>` drawer), preventing cognitive overload while maintaining complete specification access.

=== Granularity Analysis
[horizontal]
URL Permalinking Scheme:: Granular method routing (`/api/payment_intents/create`), with each parameter having its own anchor target.
Overload & Multi-Language Switching:: Toggling the language dropdown (`?lang=python` vs `?lang=node`) dynamically re-renders:
1. The method signature (`stripe.PaymentIntent.create(...)` in Python vs `stripe.paymentIntents.create(...)` in Node).
2. The parameter notation (`snake_case` kwargs in Python vs `camelCase` object fields in Node).
3. The response typing (Python SDK instance vs TypeScript interface).
Inline vs Linked Types:: Complex child objects expand directly inline within nested parameter cards, showing exact child types and descriptions.

== 3. Within-Level Differentiation

=== Sibling Entity Disambiguation
When multiple parameters inhabit the same level in a request payload:

[horizontal]
Grouping Strategy::
1. **Primary Parameters**: Required parameters appear at the very top of the list with red `required` pills.
2. **Optional Parameters**: Alphabetical list of standard optional arguments.
3. **Secondary Parameters**: Tucked under a "More parameters (24)" expandable disclosure.
Kind Identifiers::
* **Status Badges**: High-contrast pills: `required` (Red), `optional` (Subdued grey), `deprecated` (Amber).
* **Type Pills**: Monospace type annotations: `string`, `integer`, `boolean`, `dictionary`, `timestamp`.
Typographic Treatment::
* Parameter names use bold monospace font (`font-weight: 600`, `font-family: monospace`).
* Sub-types and parent prefixes use muted grey text.

[cols="1,1,2,2", options="header"]
|===
| Parameter State | Badge Label | Badge Color / Style | Visual Distinction Mechanism
| Required Field | `required` | `#df1b41` (Rose red pill) | Positioned immediately next to parameter name

== Unique Innovations & Failure Modes

=== Standout Design Innovations
* **Dual-Column Synchronized Layout**: The left-side parameter specification / right-side sticky code container represents the industry gold standard for API reference UX.
* **Tiered Parameter Exposure**: Separating arguments into **Primary** vs **"More parameters"** disclosure prevents wall-of-text fatigue for APIs with 50+ optional fields.
* **Language-State Persistence**: Changing to Python or Node updates the entire documentation experience seamlessly, swapping signatures, argument casing, and code samples simultaneously.
* **Stateful Required Badges**: High-contrast red pills ensure that mandatory parameters are visually undeniable during scanning.

=== Critical Anti-Patterns / Friction Points
* **Heavy Frontend Footprint**: The single-page hydration payload (`window.__INITIAL_STATE__`) exceeds 3.4MB, which can cause high memory usage on low-end mobile devices.
* **Non-Trivial Build Pipeline**: Requires a dedicated content management platform (Markdoc + React + CMS) that cannot be replicated with simple static markdown scripts.

=== Transferable Principles for Future Autodoc Systems
1. *The Dual-Column Presentation Principle*: Separate conceptual reference / parameter lists from executable code samples using a split layout where code remains pinned during scrolling.
2. *Tiered Argument Disclosure*: For functions with many arguments, show essential / required arguments first and fold secondary options into an expandable drawer.
3. *Explicit Required Badges*: Do not rely on subtle asterisks (`*`) or prose hints; use high-contrast semantic badges to denote required fields.
